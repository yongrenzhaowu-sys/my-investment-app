### 3. V2 APIキー方式への移行理由
ユーザーからの要望：
> リフレッシュトークンではなくて、j-quantsV2のAPIキー形式を使用してほしい

**V2方式のメリット**:
- APIキーは長期有効（リフレッシュトークンのような頻繁な更新不要）
- 認証フローがシンプル（HTTPヘッダーに `x-api-key` を追加するだけ）
- V2エンドポイントは最新機能に対応

### 4. スクリプトの全面書き換え

#### scripts/fetch_jquants_data.py の主要変更点

| 項目 | V1（旧） | V2（新） |
|------|---------|---------|
| **認証方式** | リフレッシュトークン → IDトークン（2段階） | APIキー（1段階） |
| **ベースURL** | `https://api.jquants.com/v1` | `https://api.jquants.com/v2` |
| **認証ヘッダー** | `Authorization: Bearer {id_token}` | `x-api-key: {api_key}` |
| **環境変数** | `JQUANTS_REFRESH_TOKEN` | `JQUANTS_API_KEY` |
| **日足エンドポイント** | `/prices/daily_quotes` | `/equities/bars/daily` |
| **財務エンドポイント** | `/fins/statements` | `/fins/summary` |
| **レスポンスキー** | `daily_quotes`, `statements` | `data` |
| **列名形式** | V1形式（Open, High等） | V2短縮形（O, H等）→ V1互換に自動変換 |

## 決めたこと

### 1. 認証方式の変更
- **V1（リフレッシュトークン方式）を廃止** → **V2（APIキー方式）に移行**
- **理由**: ユーザー要望 + 長期有効 + シンプル + 最新機能対応

### 2. V2短縮列名の互換性対応
V2 APIは短縮列名（O, H, L, C, Vo等）を使用するが、既存分析コードはV1形式（Open, High, Low, Close, Volume等）を前提としている。

**対応策**: スクリプト内で自動変換
```python
column_map = {
    "O": "Open", "H": "High", "L": "Low", "C": "Close",
    "Vo": "Volume", "AdjC": "AdjustmentClose", ...
}
df = df.rename(columns=column_map)
```

### 3. 営業日カレンダーの利用
- V2の `/markets/calendar` エンドポイントで正確な営業日リストを取得
- 祝日・休日を正確に除外（旧版は平日のみで近似）
- カレンダー取得失敗時は平日のみにフォールバック

### 4. プラン別レート制限対応

| プラン | 待機時間（秒） | 推奨用途 |
|--------|---------------|---------|
| Free | 12.0 | 週次手動実行 |
| Light | 1.0 | 週次手動実行 |
| Standard | 0.5 | 週次/日次実行（推奨） |
| Premium | 0.12 | 日次自動実行 |

## 学んだこと・注意点

### 1. V2 APIのメリット
- **長期有効**: APIキーは期限切れが少ない（リフレッシュトークンは頻繁に更新が必要）
- **シンプル**: 認証ヘッダーに `x-api-key` を追加するだけ
- **最新機能**: 営業日カレンダーAPI等、V2限定の便利機能あり

### 2. V2の短縮列名
- V2は列名が短縮形（O, H, L, C, Vo等）
- 既存分析コードはV1形式（Open, High, Low, Close, Volume等）を前提
- スクリプト内で自動変換して互換性を保つ

### 3. 営業日カレンダーの重要性
- 土日だけでなく祝日・年末年始も正確に除外
- V2の `/markets/calendar` エンドポイントで正確な営業日リストを取得
- フォールバック機能（平日のみ）も実装

### 4. プラン別レート制限
- Free: 12秒待機（月5,000リクエスト）
- Light: 1秒待機（月50,000リクエスト）
- Standard: 0.5秒待機（月100,000リクエスト）
- Premium: 0.12秒待機（月500,000リクエスト）

### 5. 既存データとの統合
- V2で取得したデータもV1互換の列名に変換されている
- legacy/_inbox のデータとそのまま結合可能
- `data/curated/` に統合データを保存する方式を推奨

### 6. リトライロジック
- レート制限エラー（429）時は待機時間を2倍にしてリトライ
- 最大3回リトライ
- エラーログに記録して継続
